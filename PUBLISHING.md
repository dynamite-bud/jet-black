# Publishing & distribution plan

How jet-black reaches other people. Four tiers, cheapest → broadest reach.
The single source of truth stays `schemes/jet-black.yaml`; everything below is
generated by `./build.sh`, so a palette change re-flows everywhere.

## Tier 0 — the GitHub repo (done)
`github.com/dynamite-bud/jet-black` is public. Anyone can already:
- clone it and point their tool at `jet-black-<tool>/…`, or
- copy a single file (e.g. `jet-black-ghostty/jet-black.conf`).

**To add:** a one-liner installer and a screenshot in the README.
- `curl -fsSL …/install.sh | bash` style (guarded), or `brew tap dynamite-bud/jet-black`.
- A palette swatch image + per-tool screenshots (biggest driver of adoption).

## Tier 1 — editor marketplaces (vscode + cursor)
The two highest-value targets; users install in one click.
- **VS Code Marketplace** via `vsce`: needs a *publisher* (Azure DevOps org) and a PAT.
- **Open VSX** (Cursor, VSCodium, Theia) via `ovsx`: needs an open-vsx.org account + PAT.
- `./publish.sh` already wraps both (`VSCE_PAT` / `OVSX_PAT` from env).

**Prereqs before first publish:**
1. Create the VS Code publisher + Open VSX namespace (`rudra`).
2. Add an `icon.png` (128×128) to each extension folder and re-add the `icon` field.
3. Fill `package.json` repository/homepage/categories (mostly done).
4. `./publish.sh --dry-run` → inspect the `.vsix` → then publish with tokens set.
5. Tag the release (`git tag vscode-v0.1.0`) and bump `version` per release.

## Tier 2 — tinted-theming scheme (broadest CLI/terminal reach)
This is the big one. Contribute `jet-black.yaml` to **`tinted-theming/schemes`**.
Once merged, *anyone* with `tinty` gets jet-black across **all 70+ tinted apps**
(ghostty, kitty, alacritty, tmux, fzf, bat, vim, …) with:
```sh
tinty install && tinty apply base24-jet-black
```
**Steps:** fork `tinted-theming/schemes`, add `base24/jet-black.yaml` (already
spec-valid), open a PR. Their CI validates the scheme. No per-app work — the
community templates consume it. This is how jet-black becomes "a theme people
can just pick," not a repo they must clone.

## Tier 3 — terminal theme collections
Terminals bundle theme lists from upstream repos. Submitting the palette puts
jet-black in their built-in pickers (no install needed by users).
- **`mbadolato/iTerm2-Color-Schemes`** — the upstream that **ghostty, kitty,
  alacritty, wezterm, windows-terminal, …** import. One PR → many terminals.
  Generate the iTerm2 `.itermcolors` from the scheme (tinted-terminal has an
  iterm2 template) and submit.
- ghostty also accepts theme PRs directly to its theme directory.

## Release hygiene (all tiers)
- **Semver per artifact**: editor extensions version independently in their `package.json`.
- **`git tag` + GitHub Releases** with notes; attach built `.vsix` files.
- **CHANGELOG.md** at the repo root.
- **One source of truth**: never hand-edit `jet-black-*/` outputs — edit the
  scheme, run `./build.sh`, commit. CI idea: a GitHub Action that runs
  `build.sh` + `dev/validate-contrast.py` on every PR and fails on drift.

## Recommended order
1. Screenshots + README polish (Tier 0) — makes everything else worth clicking.
2. tinted-theming PR (Tier 2) — biggest reach for least ongoing work.
3. Editor marketplaces (Tier 1) — once you have icons + accounts.
4. iTerm2-Color-Schemes PR (Tier 3) — terminal pickers.
